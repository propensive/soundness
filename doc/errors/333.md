# `SN-333` — `Moment.Error`

Raised when Aviation cannot determine a civil date-time value.

## Cause

A `Moment` is a date, a clock time and a timezone together, and this is the
error raised by every operation that builds one: parsing text against a
format, constructing a date in a calendar, naming a month, and grounding a
wall-clock time to an instant. The message is `the date was not valid
because $reason`.

Durations are not moments, so a duration that fails to parse raises
`Timespan.Error` (`SN-334`) rather than a variant of this.

## Variants

### `SN-333.1` — `Format`

The input did not match the date format being parsed.

**Example.** `[↯SN-333.1] the date was not valid because 2026-13-01 does not conform to format ISO-8601 (... at ...)`

**Resolution.** Pass an input that matches the format, or choose a
format that matches the input.

### `SN-333.2` — `Invalid`

The numeric components form a date that does not exist in the
chosen calendar (e.g. February 30 in the Gregorian calendar).

**Example.** `[↯SN-333.2] the date was not valid because 2026-2-30 does not exist in the calendar Gregorian`

**Resolution.** Adjust the day, month, or year to a valid combination.

### `SN-333.3` — `Unknown`

A textual value did not name a recognised date kind (e.g. day name,
month name).

**Example.** `[↯SN-333.3] the date was not valid because foo is not a recognized weekday`

**Resolution.** Use one of the documented names for the kind.

### `SN-333.4` — `Gap`

A wall-clock time names an instant that does not exist, because the clocks moved forward past it.

**Example.** `[↯SN-333.4] the date was not valid because the wall-clock time does not exist in its timezone (a spring-forward DST gap)`

**Resolution.** Choose a `GapPolicy`: the default pushes the time forward past the gap, and others push it backward or raise this error. Import the policy that suits the application.
