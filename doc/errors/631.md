# `SN-631` — `Upgrade.Error`

Raised when a daemon cannot stage an upgrade for its launcher.

## Cause

An Ethereal application can replace its own binary by staging the new one as
`<data>/<name>/.pending`, which the launcher verifies and swaps in at the start of its next
invocation. This error covers a source that could not be read, an application name that is not
available (the daemon was not started by a launcher), and a `.pending` file that could not be
written. A candidate the launcher rejects is not an error here: it is reported afterwards by
`Upgrade.outcome`.

## Variants

### `SN-631.1` — `CannotReadSource`

**Example.** `[↯SN-631.1] the upgrade source could not be read`

### `SN-631.2` — `CannotWritePending`

**Example.** `[↯SN-631.2] the .pending file could not be written`

### `SN-631.3` — `CannotResolveName`

**Example.** `[↯SN-631.3] the running application's name is not available`

## Resolution

Run the application through its XEK launcher, which passes the daemon its name, and make sure
the data directory (`$XDG_DATA_HOME`, `~/.local/share` or `%LOCALAPPDATA%`) is writable. Check
`Upgrade.enabled` before offering an upgrade: an executable built without a release key and an
application id refuses every candidate.
